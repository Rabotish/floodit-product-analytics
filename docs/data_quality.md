# Data Quality

Проверка качества исходных Firebase Analytics данных перед построением аналитических сущностей и расчетом продуктовых метрик.

Подробные SQL-запросы находятся в `sql/profiling/`.

**Ниже будет представлена краткая сводка профилирования, более подробно с описательными характеристиками можно ознакомиться после таблицы**

## Краткая сводка профилирования

Критических дефектов, делающих источник непригодным для продуктового анализа, не обнаружено. При этом выявлен ряд особенностей и ограничений, которые необходимо учитывать при построении аналитических сущностей и интерпретации результатов.

| Область | Основной результат профилирования | Влияние на анализ |
|---|---|---|
| Покрытие источника | 114 последовательных daily-таблиц без пропусков; каждая содержит ровно 50 000 событий | Dataset является фиксированной публичной demo-выборкой и не отражает полный объём реального трафика |
| Идентификация пользователей | `user_pseudo_id` заполнен во всех 5,7 млн событий; `user_id` полностью отсутствует | Доступен стабильный технический идентификатор пользователя, но отсутствует авторизованный `user_id` |
| Первое взаимодействие | `first_open` наблюдается только у 4 319 из 15 175 пользователей; `user_first_touch_timestamp` заполнен и стабилен для всех пользователей | `first_open` имеет неполное покрытие и не может самостоятельно описывать начало пользовательской истории |
| Временные поля | `event_timestamp` заполнен полностью; `event_date` совпадает с UTC-датой только в 66,04% случаев и с датой `America/Los_Angeles` — в 99,98% | Календарная дата и точная временная метка представляют разные аспекты времени события |
| Дополнительные timestamps | `event_previous_timestamp` содержит NULL и аномальные значения; `event_server_timestamp_offset` содержит пропуски и экстремальные значения | Эти поля не являются надёжными самостоятельными источниками порядка пользовательских событий |
| Дубликаты | Обнаружено 59 дополнительных полностью идентичных строк из 5,7 млн событий; совпадение технической сигнатуры не всегда означает полный дубль | Общий уровень raw-дубликатов крайне низкий, но технические совпадения требуют различать exact и логические дубли |
| Структура `event_params` | Каждый параметр заполнен ровно в одной типизированной ветке; часть числовых параметров представлена как через `int_value`, так и через `double_value` | Перед аналитическим использованием требуется унификация числового представления |
| `user_properties` | Структура технически согласована, но coverage сильно различается; отдельные свойства меняются внутри пользователя | Отсутствие свойства нельзя интерпретировать как значение по умолчанию, а часть свойств имеет временную природу |
| Gameplay-параметры | `level` имеет более полное покрытие, чем `level_name`; `board` заполнен во всех исследованных quickplay-событиях; у 1 272 `level_complete` отсутствует игровой ключ | Основные gameplay-сущности в целом хорошо восстанавливаются, но часть progressive events остаётся без определённого уровня |
| Gameplay-последовательности | Обнаружены timestamp-коллизии, логические дубли, повторные start и нестабильный наблюдаемый порядок связанных событий | Простое связывание событий только по времени недостаточно для надёжной реконструкции игровых попыток |
| Связь start → terminal | Для terminal-событий часто находится предыдущий start того же игрового ключа, однако распределение интервалов имеет длинный хвост; 98,92–99,56% matched events внутри наблюдаемой сессии находятся в пределах 30 минут | Полная пользовательская история наблюдается не всегда, поэтому reconstruction должна учитывать как игровой ключ, так и временные ограничения |
| `level_end` и результат | `level_end` тесно связан с `level_complete` / `level_fail`, но может наблюдаться как до, так и после явного результата | `level_end` не является самостоятельным однозначным признаком исхода попытки |
| Внутренние покупки | Наблюдается только 27 `in_app_purchase`; ключевые поля покупки заполнены, но `product_name`, `validated` и `event_value_in_usd` имеют системные пропуски | Структура IAP пригодна для анализа, но количественные выводы о монетизации ограничены малым числом наблюдений |
| Extra steps / virtual currency | `use_extra_steps` и `spend_virtual_currency` имеют близкую структуру, но не демонстрируют однозначного соответствия между событиями | Два типа событий нельзя считать техническими дублями одного действия |
| Общая применимость | Источник является публичным наблюдательным demo dataset с неполной пользовательской историей | Анализ позволяет выявлять наблюдаемые паттерны и взаимосвязи, но не гарантирует полноту событий и не позволяет делать причинные выводы |

Все правила преобразования, необходимые для построения staging и intermediate-слоёв, фиксируются в `docs/data_processing_rules.md`.

### Ограничение источника

Во всех 114 дневных таблицах представлено ровно 50 000 событий, следовательно распределение не рассматривается как естественный дневной объём активности приложения и указывает на фиксированный объём выборки, используемой в публичном demo dataset.

В официальном описании источника зафиксировано, что набор представляет собой выборку обфусцированных событий и может иметь ограниченную внутреннюю согласованность.

- число событий по дням не используется для оценки реальной динамики общего трафика приложения;
- количество наблюдаемых пользователей за день не интерпретируется как полный DAU;
- результаты, зависящие от полноты пользовательской истории, в частности последовательности событий и retention, должны учитывать неполноту demo dataset.

Календарное покрытие источника полное: пропуски daily-таблиц внутри наблюдаемого периода отсутствуют,`event_date` согласован с `_TABLE_SUFFIX`.

### Смешанное числовое представление

Некоторые логические параметры представлены и в `int_value`, и в `double_value`.

| Параметр | `int_value` | `double_value` | Дробные `double_value` | Статус |
|---|---:|---:|---:|---|
| `firebase_screen_id` | 5 186 729 | 383 147 | 0 | WARNING |
| `level` | 48 216 | 462 314 | 0 | normalization |
| `score` | 23 944 | 218 107 | 0 | normalization |
| `time` | 2 207 | 142 546 | 0 | excluded |
| `value` | 208 139 | 76 235 | 0 | normalization |

Для всех перечисленных параметров `double_value` фактически содержит целые значения.

### `level`

Значения находятся в диапазоне 0–31, не имеют дробной части, `int_value` и `double_value` рассматриваются как два технических
представления одного целочисленного параметра.

### `score`

Значения находятся в диапазоне 0–21 и не имеют дробной части, могут быть приведены к `INT64`.

### `firebase_screen_id`

Значения в `double_value` не имеют дробной части, однако достигают порядка ±9.22e18. `FLOAT64` не гарантирует точное представление всех целых
значений такого масштаба.

### `time`

Во всех 144 753 случаях логическое значение параметра равно нулю:

- `int_value = 0` — 2 207 записей;
- `double_value = 0.0` — 142 546 записей.

### `value`

Параметр представлен через `int_value` и `double_value`, не содержит дробной части.

### Коллизии `event_timestamp`

`event_timestamp` в большинстве случаев позволяет однозначно упорядочить gameplay-события пользователя, однако обнаружены случаи, когда несколько событий имеют одинаковую временную метку.

### Последовательность событий после `level_start`

| `level_retry` | 4 539 | 81,93% |
| `level_reset` | 354 | 81,07% |

Для `level_start → level_start` наиболее характерно движение на следующий уровень: медиана `level_delta = +1`.

Для `level_start → level_complete` и `level_start → level_end` медиана составляет `-1`.

Оба наблюдения соотносятся с логикой игры, дополнительные проверки позволяют заключить, что переход `level_start → level_complete` и `level_start → level_end` к предыдущему уровню обусловлен задержкой в логировании. Отсюда следует, что terminal-событие нельзя автоматически сопоставлять с ближайшим предыдущим `level_start` без учёта `level`.

- `value` заполнен и находится в диапазоне 1–20;
- `item_name` заполнен.

Поскольку структура и значения двух типов событий близки, дополнительно проверена их временная связь.

Совпадений `spend_virtual_currency` и `use_extra_steps` одного пользователя на одинаковом `event_timestamp` не обнаружено.

Для `use_extra_steps` событие `spend_virtual_currency` с теми же `value` и `item_name` наблюдается в пределах 30 секунд в 57,00% случаев.

Для `spend_virtual_currency` соответствующее `use_extra_steps` наблюдается в пределах 30 секунд в 54,35% случаев.

Отсюда следует, что два event type нельзя считать техническими представлениями одного и того же события.

## 11. Границы применимости данных

Источник является публичным demo dataset и не гарантирует полноту пользовательской истории, то есть отсутствие наблюдаемого события
не всегда означает отсутствие соответствующего пользовательского действия, а реконструируемые последовательности, сессии и игровые попытки описывают
только наблюдаемую часть поведения пользователя.

Небольшое число `in_app_purchase` ограничивает надёжность количественных выводов о монетизации.

Данные являются наблюдательными; обнаруженные связи между поведением пользователя и последующими метриками не интерпретируются как причинно-следственные эффекты.

Ограниченный период наблюдения создаёт правую цензуру при расчёте retention: для пользователей, впервые появившихся в конце периода, полный горизонт D1/D7 недоступен.
