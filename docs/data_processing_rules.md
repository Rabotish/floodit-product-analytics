# Data Processing Rules

Раздел посвящен описанию правил предобработки данных.

## Общие правила staging

### Идентификация пользователя

`user_pseudo_id` - основной идентификатор пользователя.

### Временные поля

Для календарных разрезов дата события определяется как: `PARSE_DATE('%Y%m%d', event_date)`.

`event_timestamp` - основная временная метка для упорядочивания наблюдаемых событий.

`event_date` - атрибут для формирования календарных группировок и построения дневных продуктовых метрик, не пересчитывается из `event_timestamp`.

Минимальный `event_timestamp` пользователя не используется вместо `user_first_touch_timestamp`.

`event_previous_timestamp` не используется для восстановления последовательности событий.

`event_server_timestamp_offset` не включается в аналитическую модель.

### Дедупликация

При подготовке staging-слоя удаляются только полностью идентичные строки исходного Firebase export.

Совпадение отдельных технических атрибутов события, включая `user_pseudo_id`, `event_timestamp`, `event_name` и `event_bundle_sequence_id`, не считается достаточным условием для удаления записи.

Внутри одного события значения `event_params.key` уникальны. Аналогично, внутри одной строки значения `user_properties.key` уникальны.

При извлечении конкретного параметра дополнительная агрегация или дедупликация элементов массива не требуется.

### Нормализация `event_params`

Значение параметра представлено ровно в одной типизированной ветке `event_params.value`.

**`level`**

Нормализуется в `INT64`: `COALESCE(int_value, CAST(double_value AS INT64))`

**`score`**

Нормализуется в `INT64`: `COALESCE(int_value, CAST(double_value AS INT64))`

**`value`**

В исследуемом датасете оба числовых представления содержат целые значения.

Нормализуется в `INT64`: `COALESCE(int_value, CAST(double_value AS INT64))`

Бизнес-смысл `value` определяется только в контексте `event_name`.

**`firebase_screen_id`**

Не используется как ключ аналитической модели.

Для анализа экранов используются `firebase_screen` и `firebase_screen_class`.

**`time`**

Параметр исключается из аналитического слоя.

## Пользовательские атрибуты

### Определение нового пользователя

`first_open_time` - бизнес-атрибут времени первого открытия приложения.

`user_first_touch_timestamp` - технический атрибут времени первого открытия, который непосредственно используется в аналитической модели.

Пользователь новый, если время первого открытия попадает в период формирования new-user cohort.

`first_open` - дополнительный диагностический маркер первого открытия, при диагностических проверках используется самое раннее наблюдаемое событие.

### Обработка `user_properties`

- `value.*` хранит значение свойства;
- `set_timestamp_micros` хранит момент его установки или обновления.

Отсутствие свойства не преобразуется автоматически в `false`, `0` или другое значение по умолчанию.

Для свойств, которые меняются во времени, используется значение, актуальное на момент анализируемого события.

`ad_frequency`, `initial_extra_steps`, `_ltv_*` могут изменяться во времени, используются в состоянии, актуальном на момент анализируемого события.

`firebase_exp_*` - не используются как безусловно статические признаки без предварительной проверки стабильности назначения группы.

`plays_progressive` и `plays_quickplay` принимают наблюдаемое значение `true`, отсутствие свойства не интерпретируется как `false`.

`first_open_time` хранится в `int_value` как Unix timestamp в микросекундах и преобразуется через: `TIMESTAMP_MICROS(int_value)`.

### Платформа

`platform` - основной атрибут платформы.

`device.operating_system` не используется как отдельный источник платформы.

### Источник установки

Единый источник установки формируется как: `COALESCE(app_info.install_source, app_info.install_store)`.

## Gameplay intermediate

### Логические дубликаты gameplay

После удаления полностью идентичных raw-строк для gameplay-событий дополнительно применяется проверенное правило логической дедупликации.

События с одинаковыми:

- `user_pseudo_id`;
- `event_timestamp`;
- `event_name`

схлопываются в одну запись в intermediate gameplay-слое.

Правило применяется только к gameplay-событиям и не распространяется на остальные типы событий.

Повторные start-события одного `level` или `board` на разных timestamp не считаются дубликатами.

### Игровой ключ и атрибуты уровня

`level` - основной числовой атрибут уровня для progressive gameplay.

`level_name` - дополнительное описательное поле, согласованное текстовое представление `level`.

Если `level` отсутствует, значение не восстанавливается из `level_name` и соседних событий.

Если `level` заполнен, отсутствующий `level_name` может быть восстановлен как: `CONCAT('level_', CAST(level AS STRING))`.

События `level_complete` без `level` сохраняются, для них `level` не восстанавливается из соседних событий, также они не участвуют в level-based реконструкции attempts и сохраняются с неизвестным игровым ключом.

`board` - основной атрибут конфигурации игрового поля для quickplay.

### Реконструкция игровых попыток

В рамках реконструкции attempts к terminal-событиям относятся:

- `level_complete` / `level_complete_quickplay`;
- `level_fail` / `level_fail_quickplay`;
- `level_end` / `level_end_quickplay`.

`user_pseudo_id + level` - ключ для progressive mode.

`user_pseudo_id + board` - ключ для quickplay mode.

Terminal-событие сопоставляется со start, если:

1. совпадает `user_pseudo_id`;
2. совпадает игровой режим;
3. совпадает `level` или `board`;
4. start расположен раньше terminal;
5. между start и terminal нет наблюдаемого `session_start`;
6. интервал между событиями не превышает 30 минут.

Если найдено несколько подходящих start, используется последнее предшествующее событие.

Terminal без подходящего start сохраняется как unmatched.

Повторные start одного игрового ключа на разных timestamp не дедуплицируются.

### Наблюдаемые границы сессии

`session_start` используется как наблюдаемая граница gameplay-сессии.

Игровая попытка не может пересекать зарегистрированный `session_start`.

Отсутствие нового `session_start` не считается достаточным доказательством непрерывности сессии, поэтому граница применяется совместно с максимальным интервалом 30 минут между start и terminal.

### Результат и состояние попытки

Наблюдаемая игровая попытка создаётся по событию
`level_start` / `level_start_quickplay`.

Явный результат определяется по:

- `level_complete` / `level_complete_quickplay` → успешная попытка;
- `level_fail` / `level_fail_quickplay` → неуспешная попытка.

`level_end` / `level_end_quickplay` - дополнительный маркер окончания, не определяющий результат.

`level_reset` / `level_reset_quickplay` не создаёт новую попытку. Если событие сопоставляется с текущей попыткой, оно фиксируется как признак её сброса / прерывания.

`level_retry` / `level_retry_quickplay` не создаёт новую попытку и не используется как terminal-событие, сохраняется как поведенческий
маркер повторного прохождения.

Новая наблюдаемая попытка начинается только при последующем `level_start` / `level_start_quickplay`.

Если для сопоставленной попытки присутствует `level_end`, но отсутствуют `complete` и `fail`, результат задаётся как неизвестный.

Порядок `complete/fail` и `end` внутри одной попытки не используется для определения результата, поскольку в данных эти события могут наблюдаться в обоих временных порядках.

## Engagement

Событие `user_engagement` без `engagement_time_msec` сохраняется, но не участвует в расчете длительности engagement.

## Обработка monetization-событий

### Внутренние покупки

`product_id` - основной идентификатор продукта.

`product_name` - дополнительный описательный атрибут.

Покупка не фильтруется по наличию `validated`. Отсутствие `validated` не интерпретируется как невалидная покупка.

Локальная сумма покупки рассчитывается как: `price / 1000000.0` и используется только совместно с `currency`.

Raw `price` разных валют напрямую не сравнивается.

`event_value_in_usd` - сумма рассчитанная в USD, при `currency = 'USD'` сумма может быть восстановлена как:

`price / 1000000.0`.

Если валюта отлична от USD, отсутствующий `event_value_in_usd` автоматически не восстанавливается без отдельного валютного курса.

`quantity` сохраняется, в наблюдаемом наборе равен `1`.

Параметр `value` для `in_app_purchase` не используется как отдельный источник суммы.

### Rewarded-реклама

`ad_reward` - индикатор факта получения рекламной награды.

`ad_event_id` не используется как обязательный идентификатор события.

Пустая строка в `type` рассматривается как отсутствующее семантическое значение, а не как отдельный тип награды.

### Дополнительные ходы

`use_extra_steps` - индикатор факта использования дополнительных ходов.

`spend_virtual_currency` - отдельное событие расходования ресурса `steps`.

`use_extra_steps` и `spend_virtual_currency` не дедуплицируются и не объединяются в одно событие, соответственно при расчёте количества использований дополнительных ходов события двух типов не суммируются.

`no_more_extra_steps` - индикатор факта столкновения пользователя с ограничением доступных дополнительных ходов.

Числовой `value` события `no_more_extra_steps` не получает отдельной бизнес-интерпретации без дополнительного подтверждения семантики.
